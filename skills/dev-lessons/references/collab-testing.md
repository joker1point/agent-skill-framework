### C-01 大改动 PR 的四步协作法
- 场景：#开源PR
- 问题：对开源项目提大改动 PR，担心 maintainer 因"改动过大"拒绝。
- 方案（四步）：
  1. **先占坑沟通**：动手前开 issue/讨论说明意图与方案，获得 maintainer 认可；
  2. **用数据回应顾虑**：maintainer 质疑时给测试数据/基准，不空辩；
  3. **完整测试证据链**：PR 描述附复现步骤、测试输出、边界 case；
  4. **快速响应 review**：24h 内回复评论，小步提交。
- 溯源：pr/项目经验总结-MoneyPrinterTurbo-PR1291.md、luyan/docs/2026-06-28-pr-creation-experience.md

### C-02 环境变量劫持：CI 里最阴的坑
- 场景：#CI #测试
- 问题：本地测试全绿，CI 里 API 调用行为诡异。
- 根因：CI 环境预置的 `GITHUB_TOKEN` 等环境变量劫持了代码里的凭证读取逻辑。
- 方案：测试里显式清空/覆盖相关环境变量（`env.pop` / monkeypatch）；凡是读环境变量取凭证的代码，测试必须隔离。
- 溯源：pr/项目经验总结-MoneyPrinterTurbo-PR1291.md

### C-03 测试断言与初始化的低级坑
- 场景：#测试 #Python
- 问题清单（每条都真实翻过车）：
  1. 断言用子串匹配（`assert "±5" in text`），`±` 这类特殊字符/文案改动就挂——断言语义而非文案；
  2. 分支内变量未初始化：`mode=None` 路径下 `complexity` 未赋值 → `UnboundLocalError`——所有分支的变量初始化顺序要覆盖默认路径；
  3. 测试误判：age 案例中测试先于实现看懂了需求，险些按错误测试改正确实现——**测试和实现冲突时先审查测试本身的前提**；
  4. 第三方降级测试（如 503）：要验证降级路径产出而非只验证不崩。
- 溯源：2026-07-06_event_complexity_and_decision_llm_first.md、2026-07-03_age_consistency_anchor.md


### C-04 环境自适应测试必须两条分支都过：本地绿 ≠ CI 绿
- 场景：#CI #测试 #发布闸门
- 问题：新加的发布前置测试在 CI 上 **4 个 job 全红**（Windows py3.11/3.13、ubuntu、release 的 tests job），而本地一直绿；release 的两个打包 job 因此全 skipped → **tag 发出去了却零资产**。
- 根因：测试按环境自适应选入口 —— 有 `web/dist` 走 `run.py`，没有则退回 `server.py`（CI 的测试 job 不构建前端）；而启动参数是照 `run.py` 写死的（`--no-browser`）。给 `server.py` 传未知参数 → argparse `exit(2)` → 进程当场死 → 「进程活着 / health 可用」必红。**本地工作区里有 dist，所以永远只跑到 run.py 那一条分支**。
- 方案：① 环境相关的参数按入口构造（只给支持它的入口）；② 失败路径要打印能区分原因的读数（本例是 **exit code** —— 把"参数不认"与"采集层崩溃"分开）；③ 发布闸门要放在**与真实交付入口同条件**的 job 里：让 exe job 在 `npm run build` 之后跑同一条测试，才真正覆盖 `run.py`（= 用户双击的入口），只放在没有 dist 的 job 里等于没覆盖用户路径。
- 反模式：写了自适应分叉却不显式覆盖每条分支；把"本地跑过"当证据；发布闸门放在与交付形态不同的环境里。
- 溯源：flowwatch v1.0.2 发版被自家测试挡下（2026-09-23，修复提交 `25aa643`；同族 **M-10**「本地验证的假成功/假失败」、**E-12**「发布流水线自带把关」）。

### C-05 杀伤类工具的端到端验证：受控沙包 + 全量白名单，把“承诺”变成断言
- 场景：#测试 #自动化 #安全 #Windows
- 问题：新功能承诺“有窗口的进程永不被强杀（Skip）”，**怎么证明**？读代码不算；在真机上等内存临界不可复现；随便杀个进程又可能伤到用户正在跑的东西（本机当时就有一个 dev server 在跑）。
- 根因：杀伤类工具的行为只有**真的触发一次**才可信，而触发条件（内存临界）既难造、也不该强行制造。
- 方案（造一个“唯一候选”的沙包，A/B 一次断言两条分支）：
  1. **沙包**：起 `pythonw` + tkinter 窗口，`root.protocol("WM_DELETE_WINDOW", lambda: None)` **主动拒绝关闭**，再 `bytearray(250*1024*1024)` 占住内存 → 一个“有窗口且不理会关闭请求”的目标；
  2. **让它成为唯一候选**：把机器上**其余所有进程名**写进临时白名单文件（`-ProtectFile <tmp>`），守护于是只剩沙包一个候选（顺带验证了“白名单文件热加载”这条路径）；
  3. **A/B 断言**：`Skip` 跑一次 → 断言**沙包仍存活** + 日志含 `SKIP`；`Close` 跑一次 → 断言**沙包已消失** + 日志含 `ACTION stopped`；
  4. **隔离三件套**：日志写 `%TEMP%`（`-LogDir`）、白名单用临时文件、桌面告警文件**测前备份/测后还原**；没装 Python 就干净 `[SKIP]` 退出。
  关键手法：**用“白名单把世界保护起来”构造单变量实验** —— 不必控制内存，就能让守护只对沙包出手。
- 反模式：靠读代码宣称“逻辑正确”；在真机上制造内存临界来测；拿用户正在跑的真实进程当靶子（沙包必须是自己起的、名字唯一的宿主）。
- 溯源：memfuse `tests/windowed-protection.ps1`（2026-09-24 实测 exit 0 / `[PASS]`；同族 M-10、C-03「断言语义而非文案」）
