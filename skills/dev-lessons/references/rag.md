### R-01 向量入库的幂等键 = 内容哈希 + chunk 序号，预检只为省钱
- 场景：#RAG #向量库 #去重 #成本
- 问题：重复抓取/任务重跑导致内容重复入库，且 embedding 费用白付。
- 根因：入库 id 无稳定来源（自增/随机 id 重跑必重复）。
- 方案：`content_hash = sha256(url)` 作文章身份，chunk id = `{hash}_chunk_{i}`，入库走 upsert（天然幂等）；入库前 `has_article(url)`（只查 `_chunk_0`）预检，命中即跳过 —— 预检是**成本优化**，不是正确性依赖。
- 复用点：文章级计数用 `ids.endswith("_chunk_0")` 聚合（一篇一条），`collection.count()` 是 chunk 数不是文章数。
- 反模式：用 metadata 字段查重（慢且非唯一）；把预检当幂等保障（并发下会漏）。
- 溯源：vectordb-news/pipeline/crawler.py、vectordb/store.py（2026-09）

### R-02 检索范围必须显式建模"内容归属"，别只靠来源字段
- 场景：#RAG #元数据过滤 #多来源
- 问题：Agent 联网搜索/外部导入的内容 `source` 不属于任何绑定源列表 → 检索的 `source $in [...]` 过滤把它全漏掉，"入库了但用不上"（功能静默半截）。
- 根因：内容归属只靠 source 单字段表达，新增来源通道时检索侧没同步。
- 方案：入库时打归属标记（如 `topic_id: "3"`）；检索 where 用**并集**：`{"$or": [{"source": {"$in": [...]}}, {"topic_id": {"$eq": "3"}}]}`；绑定列表为空 = 不限来源（不加过滤）。
- 反模式：只加新数据源忘了改检索过滤；用字符串字段做数组包含（Chroma 的 `$contains` 只支持列表型 metadata）。
- 溯源：vectordb-news/pipeline/report_engine.py `_build_where`（2026-09-17 主动搜索入库接入时暴露）

### R-03 回看时间是产品参数：冷启动用长窗，日常用短窗
- 场景：#RAG #冷启动 #首屏体验
- 问题：新用户/新主题建好后首份报告为空（"过去 24 小时未检索到相关内容"）→ 首次体验直接劝退。
- 方案：生成函数开放 `lookback_hours` 覆盖参数；首份稿用长窗（如 7 天=168h）保证内容充实，日常定时用短窗（24h）；空结果文案按实际窗口动态生成（"过去 7 天/24 小时"），不要写死。
- 溯源：vectordb-news/pipeline/report_engine.py `generate_for_topic(..., lookback_hours)`（2026-09-17 首报快报）

### R-04 生成物幂等：DB 唯一约束 + INSERT OR IGNORE，配合"建完即生成"
- 场景：#RAG #定时任务 #幂等
- 问题：定时生成与手动补生成/新建即生成并存 → 同一周期产出多份重复报告。
- 方案：DB 层 `UNIQUE(entity_id, date)` + `INSERT OR IGNORE`，写失败返回 None → 上层识别为"已存在、跳过"；**新建实体后立即后台线程生成首份**（不等定时），定时任务到点因幂等自动跳过；后台任务异常必须 try/except 吃掉、不影响主流程。
- 反模式：业务层"先查再写"（有竞态）；同步等待生成（用户界面卡几十秒）。
- 溯源：vectordb-news/web/monitor_system.py `save_report`、web/api.py `_generate_first_report`（2026-09-17）

### R-05 LLM 产出必须做"原文溯源校验"，幻觉条目丢弃 + 降级路径
- 场景：#RAG #幻觉 #质量审核
- 问题：LLM 生成的报告条目出现库里根本不存在的内容（编造 url/标题/来源）。
- 方案：逐条校验 url 是否在**本次检索到的候选集**内 → 不在即丢弃；全部被丢弃时走 fallback（用检索到的原文直接成文）；落库状态区分 done / degraded / empty / failed，让"降级"可观测；**校验前后计数暴露到管道统计**（质量审核步）。
- 复用点：校验集合要用"本次实际检索结果"，不是全库（避免把未参与生成的旧文当合法）。
- 溯源：vectordb-news/pipeline/report_engine.py `_validate_items` / `_fallback_from_docs`

### R-06 费用闸门放生成入口；配额命中要 break 不要 continue
- 场景：#RAG #成本控制
- 问题：embedding/LLM 配额耗尽后仍逐条重试，流程卡在失败循环里空转。
- 方案：`quota.can_call` 检查放**生成入口**（在昂贵检索之前）；批量嵌入返回空 → `break` 整批停止（不是 continue 逐条撞墙）；"因配额跳过"要有独立状态（如 `skipped_quota`）并展示给用户。
- 溯源：vectordb-news/rag/quota_manager.py、pipeline/crawler.py

### R-07 向量库统计不要走全量同步扫描
- 场景：#RAG #性能 #统计接口
- 问题：知识库页面要"总文章/按归属/最近条目"统计 → 每请求全量拉 metadata 又慢又重。
- 方案：`collection.get(include=["metadatas"])`（**不带正文与 embedding**）→ 在 chunk_0 上聚合；接口加短 TTL 内存缓存（如 60s）；排序/分页在内存做（Chroma `get` 无序，也不支持 order by）；大结果集先聚合统计再切片返回。
- 反模式：每篇文章一次 `get`（N 次往返）；把 `page_content` 一起拉回来（体积爆炸）。
- 溯源：vectordb-news/vectordb/store.py `all_article_meta`、web/api.py `/api/library`（2026-09-17）

### R-08 管道可视化 = 埋点长在流程里，不是事后推算
- 场景：#RAG #可观测性 #管理台
- 问题：想展示"采集→处理→去重→…→分发"多步管道，没有真实数据可展示（只能写死或装样子）。
- 方案：每步计数在流程内埋点（采集层 fetched/deduped/chunks/new；生成层 retrieved/analysed/approved/assembled），逐层汇总进"本次运行结果"对象；对外统一 stages 数组（key/name/count/status/hint），前端只按 status 渲染状态点；**内存态统计要明说"重启清零"**，能落库的口径（如已推送数）改查 DB 保证真实。
- 溯源：vectordb-news/pipeline/crawler.py、report_engine.py `last_stats`、web/api.py `/api/pipeline/stages`（2026-09-14~17）

### R-09 报告的价值在"进化对比"，别只给静态清单
- 场景：#RAG #产品设计 #报告
- 问题：每天一份报告长得一样，用户看不出变化，"每天看"的动力为零。
- 方案：生成/展示时算 **diff**（对比上一份：新增 / 延续条目数，条目上打"新/延续"标签）；首份标"📌 基线报告（第 1 份）"并说明"明天起随新信号进化"；列表显示"第 N / 共 M 份"；👍/👎 反馈进后续排序权重（显式反馈 + 语义偏好 + 隐式画像三层重排）。
- 溯源：vectordb-news/web/static/reports.html `renderReport`（2026-09-17 进化感知）

### R-10 用户端"知识资产"视图三件套：总览 / 按主题筛选 / 导出
- 场景：#RAG #知识库 #产品
- 问题：内容持续沉淀在向量库里，但用户看不见、搜不着、带不走 → "资产"感为零。
- 方案：独立页面=总览统计（文章数 / 片段数 / 近 7 天新增）+ 按主题 chip 筛选（带计数）+ 条目列表（来源打标，如"🔍 主动搜索"区分主动发现内容）+ Markdown 导出（当前筛选范围，`Content-Disposition` 附件 + UTF-8 文件名）。
- 溯源：vectordb-news/web/static/library.html + `/api/library[/export]`（2026-09-17）

### R-11 联网搜索做"主动发现"：与订阅互补，但依赖要装对
- 场景：#RAG #Agent #联网搜索
- 问题：被动订阅（RSS/固定源）覆盖不了长尾；接上联网搜索后却毫无产出。
- 根因（实例）：`duckduckgo_search` 已改名 `ddgs`，旧包接口**静默返回空列表**（不抛异常）→ 搜索"成功"但零结果。
- 方案：`from ddgs import DDGS` 优先、旧包回退；异常静默返回空不中断主流程；每实体每次取 3-5 条、实体间 sleep 1s 限速；结果去重后入库并打归属标记（见 R-02）；把"搜索了几次/命中几条/新增几条"计入管道统计。
- 反模式：只 catch 异常不检查"返回空"（空是最常见的失败形态）；不做限速批量轰炸搜索接口。
- 溯源：vectordb-news/rag/web_search.py、pipeline/crawler.py `search_topic`（2026-09-17；另见 MEMORY 部署注意）

### R-12 检索增强的"追问"闭环：报告条目 → 对话深挖
- 场景：#RAG #交互闭环
- 问题：报告是终点，用户想深挖只能自己重新组织问题，上下文全丢。
- 方案：条目上加「追问」入口 → 跳对话页带 `?q=请展开讲讲：<标题>` → 对话页读参数自动填入并发送（**发完 `history.replaceState` 清参**，防刷新重复发送）；对话与报告共用同一知识库与检索口径，答案才能对得上。
- 反模式：新开一个独立问答页（知识库割裂）；自动发送后不清 URL 参数。
- 溯源：vectordb-news/web/static/chat.html + reports.html（2026-09-17）

### R-13 落地页宣称的能力必须逐项对照实现（口径红线）
- 场景：#RAG #产品 #对外口径
- 问题：首页宣称"四层记忆"，其中 L2（BM25/7 天 TTL）**无任何实现、纯文案** → 演示/面试被追问即穿帮。
- 方案：宣称清单逐项 grep 实现点；未实现的要么补实现、要么从文案删除；演示、文档、口述三处口径必须一致（本项目的做法：landing 保留概念层，交接文档写明"真实 = L1/L3/L4，L2 无实现"）。
- 溯源：vectordb-news/web/static/landing.html + docs/handoff/vdb-news.md「面试口径」
- **2026-09-29 修订：口子已关闭。** L2 改为真实存在的「偏好画像」层（`web/user_profile.py` 生成 + `rag/generator.py` 调用前注入 + `qa_log.profile_json` 可审计），landing / `vdb-about.html` 文案同步；做法与判断依据见 R-15。

### R-14 分块策略改版后的索引重建：原文只能还原，且必须先量化前提

- 场景：#RAG #分块 #索引重建 #破坏性操作
- 问题：改完分块器，**存量不会自动更新**；而且块数变少会留**孤儿块**。全库重刷是 `rm` 级操作，但**原文抓不回来**（RSS 是滚动窗口、本地也无原文缓存）。
- 根因：两条叠加 ——
  ① **入库幂等键 `{url_hash}_chunk_0` 让已入库文章被直接跳过**（crawler 的 `has_article` 预检），所以换分块器后旧文章永不重算；
  ② 重建后 chunk 数变化 → 旧的第 `45..142` 块仍在库里、**仍可被检索**、还带着旧格式（本次实测某篇 143 块 → 45 块，全库积了 1252 个孤儿块）。
- 方案：**先把原文还原，再重切**（相邻 chunk 是原文的连续子串，用"最长『后缀 = 前缀』匹配"去重叠）。写入顺序 **先写新块、再删孤儿** —— 中途崩溃只会"新旧并存"，绝不整篇消失，可重跑续做。重建前**必须量化 4 条前提**（都是会静默出错的地方）：
  1. **chunk 长度分布一致**：`max` 正好等于 `chunk_size`（且无一超过）→ 全库同参数，还原前提成立；
  2. **相邻块"匹配不上"的比例**：正常可高达 50~55% —— langchain 的 overlap 按 **split 粒度**施加，很多边界本就无重叠，拼起来是对的；
  3. **"疑似有重叠但边界错位"的对数必须为 0** —— 这是唯一会导致拼接**重复正文**的形态（判据：尾部与头部的最长公共子串 ≥60 但它不是前后缀关系）。用一个"已验证过"的数据集做对照：本次线上 0 处、本地旧语料 0 处，且**还原比 0.8911 逐位相同**；
  4. **是否有"新形态"块混在里面** → 见下面反模式。
  重建后必查：总量 / 文章数 / 旧格式残留 / **时间戳字段是否仍为数值**（写成字符串会让时间窗过滤 `{"$gte": 数值}` **静默匹配不到**，检索返回空且日志不报错）。另：**改版只对今后新入库的内容生效**，所以"代码上线"≠"库里已统一"。
- 反模式：⚠️ **分块器改版后，绝不能在"新旧形态混杂"的库上重建。** 新分块器给**每一块**都加了标题前缀，而旧块只有首块带 → 还原时"后缀=前缀"匹配不上，拼接会把**标题串进正文中间**（143 块的长文会串 142 次）。判据很简单：**非首块是否都以 `标题\n` 开头**（全是以新形态计）。本机实测对照极清晰：旧形态语料 `boundary_shift=0`、还原比 0.8911（可重建）；新形态语料 `boundary_shift=369`、还原比 1.000（一点没去重，重建即污染）。**其余反模式**：不备份就重建（必须服务器侧副本 + 打包异地双保险）；只信 dry-run 的总量而不与历史比例对照；重建后只看"总量对不对"而不查字段类型。
- 溯源：vectordb-news `pipeline/rebuild_index.py` + `evals/diag_overlap.py`（2026-09-28，本地 590 篇 1959→1120、线上 962 篇 2976→1726 两次实战）

### R-15 反馈 → 画像 → 调用前注入：缺的往往不是"记忆层"
- 场景：#RAG #个性化 #上下文工程
- 判断（先做对判断，再写代码）：产品需要"越用越懂你"时，**先看反馈链路是否闭合，别急着上记忆层**。典型症状 = 反馈采到了（👍/👎 + 归因标签）、但没有任何地方把它回写成画像、更没注入给模型。此时加一层"短期记忆检索"（向量/关键词）通常**收益低**：语料本身就是记忆（知识库），多轮指代已由会话记忆 + 改写解决；真正的缺口是"反馈 → 画像 → 每次调用前读取"这一环。判断依据：① 会话内的连贯问题已被会话记忆覆盖吗？② 语料检索是否已经解决了"事实从哪来"？③ 剩下的个性化需求是**偏好**（取舍与表达）还是**事实回忆**？是偏好 → 做画像，不要做记忆检索。
- 方案（最小闭环，约半天）：
  1. **画像生成**：只读聚合现有信号（问答埋点表 + 反馈表 + 兴趣词 + 用户主题），规则优先、不引入新写路径；**样本不足（如 <3 条）不生成**——不拿噪音当结论。
  2. **注入点选在最窄的咽喉**：LLM 调用的提示词组装函数（如 `_compose_system_prompt(context, profile_block)`），不要在每个调用方各拼一遍；**空画像时提示词必须与旧版逐字节一致**（可对照、可回滚）。
  3. **四条纪律**：① **旁路，绝不抛异常**（画像炸了 = 不注入，主流程照常，且要有单测钉住）；② **画像不是事实**——免责行写进注入块（"只影响取舍与表达，不得当作事实依据"），否则模型会拿画像当证据；③ **有预算**（如 ≤600 字，空画像不留空标题、不浪费 token）；④ **可审计**——把注入内容/摘要落库（新增一列，随埋点行走），离线就能回答"这一轮到底注入了什么"。
  4. **缓存与失效**：画像按用户缓存（如 300s），但**反馈提交后必须 invalidate**——画像 = 反馈的函数，缓存旧版本等于反馈不生效。
  5. 文案与实现同步（见 R-13）：把原先"宣称但没有实现"的那一层**替换成真正做出来的东西**，比补一个自己都不信的功能更划算。
- 反模式：把画像塞进"记忆层"叙事里当成向量检索来做；画像里放可能过期的具体数字（模型会当事实）；注入块放在系统提示开头就以为"更重视"（先测位置再定）；改了注入但没落库，事后无法解释某轮为什么答成这样。
