### V-01 带时间窗的评测必须锚定"基准日"，否则报告隔周不可复现

- 场景：#评测 #可复现性 #时间窗
- 问题：重跑一份既有报告，**四个带时间窗的配置分数集体从 43% 跌到 8.8%**，看起来像严重回归。
- 根因：窗口用 wall-clock 算（`cutoff = time.time() - 7*86400`）。数据（滚动窗口抓取的语料）最新一条停在 7 天前 → **窗内只剩 10 篇**，带窗配置等于"在 10 篇里检索"。失败方式是**分数下降**，不是报错。
- 方案：加 `EVAL_AS_OF` 环境变量把窗口锚在固定日期（支持 `YYYY-MM-DD` 与 ISO 串），**不设时行为不变**（纯增量、不破坏历史可比性）。报告头自动记录**基准日 + 数据目录**，让报告自证数字怎么来的。锚定有效性要自测：用同一份旧数据在固定基准日下重跑，与历史报告偏差应 ≤1pp（实测 0.6pp）。
- 反模式：用"今天"跑出来的数字做跨周对比；把"窗口被饿死"导致的下降解释成模型/代码退化，然后去优化一个不存在的问题。
- 溯源：vectordb-news/evals/recall_eval.py（2026-09-28；报告头记录 `EVAL_AS_OF` + `CHROMA_DIR`）

### V-02 对照实验两边必须跑满同一查询集：judge 失败是随机的，剔除样本会静默抬高均值

- 场景：#评测 #A/B #LLM-judge
- 问题：A/B 两组的结果"能算"，但两组的**成功查询集不同** —— 一组 18/18、另一组 17/18。被剔除的查询恰好是某配置的**低分样本** → 那组均值被整体抬高，差值里有一部分是假的。
- 根因：judge 失败是**随机**的（同日三次跑分别失败不同查询、还有一次 0 失败），而"剔除失败样本"这个动作是确定的。均值对分母极敏感。
- 方案：任何要写进结论的对比，**两边必须跑满同一查询集** —— 不达标就重跑到齐；报告头记录**成功数 / 总数 / 失败清单**；把"n 不一致"当**阻断条件**而不是脚注。
- 反模式：在 n 不一致的两组之间直接比均值；只写"成功 N 条"不写"总 M 条、失败哪几条"。
- 溯源：vectordb-news 语料 A/B 对照（2026-09-28）

### V-03 n 小的时候报置信区间，不要比均值 —— 差值连正负都保不住

- 场景：#评测 #统计 #小样本
- 问题：同一对配置的差值，**旧数据 +2.2%、新数据 −1.1%（符号翻转）**，n=18。
- 根因：小样本下"配置间差值"的方差大于差值本身，比均值等于比噪声。
- 方案：报**配对 bootstrap 95% CI**（配对 = 同一查询、同一判定，能消掉题目难度差异）；CI 跨 0 就写"观测到正向趋势，**未达显著**"。想要结论必须先扩 n，没有别的路。
- 反模式：单次测量就写"提升 X%"；CI 跨 0 还写"有提升"；靠调分母（剔除某些样本）把数字做过阈值。
- 溯源：vectordb-news/evals/compare_gen_reports.py（2026-09-28，逐题配对 bootstrap）

### V-04 每个数字都要带"数据版本"：换语料，结论会变

- 场景：#评测 #数据版本 #口径
- 问题：同一套代码、同一个基准日，**只换语料**：
  - `AB vs A` 从 **+10.6pp → +2.2pp**；`AR vs A` 从 +8.3pp → +3.9pp
  - 生成层 Faithfulness `0.905 → 0.887` —— 但**不能**直接比：新题集从 20 题扩到 55 题、覆盖更均衡，难度上升本身就会让指标下降（在共享的 20 题子集上两次独立运行 Δ = **0.000**，这才是"测量链稳定"的证据）
- 根因：数据是随时间增长 / 变化的（RSS 是滚动窗口，语料每月都在变），检索类指标对数据分布高度敏感。
- 方案：报告头固定记录**数据版本 + 基准日**；跨环境 / 跨周引用任何数字时**显式标注数据版本**；换数据后旧结论作废，**不要混用**。要证明"指标变化来自改动"而不是"来自数据"，就用**只换数据、其余冻结**的对照。
- 反模式：拿上周报告的 X% 与本周的 Y% 直接相减；在语料不同的两个环境之间比绝对分。
- 溯源：vectordb-news `evals/eval_report_{v4_baseline,oldchunk,newchunk}.md`（2026-09-28）

### V-05 增益要问一句"它到底在补偿什么"：部分替代关系会伪装成独立价值

- 场景：#评测 #A/B #归因
- 问题：某组件（多路召回 / BM25 字面路）显示 **+10.6pp** 的巨大增益，像是核心功臣。清洗语料后，同一对比只剩 **+2.2pp**。
- 根因：原语料含大量 HTML 标签（26~38%），稀释了向量检索质量；BM25 字面路恰好能绕过噪声捞回一部分。**脏数据下它在补偿清洗的缺失，不是独立的互补召回能力。** 两个手段部分是**替代**关系，不是叠加关系。
- 方案：见到大增益先问"它在补偿哪个缺陷"，做法 = **把疑似缺陷修掉再测同一对比**；若增益大幅缩水，就证明是补偿而非叠加。对照设计要用"**只换一个变量**"（如只换语料的两组），而不是"加组件 / 去组件"。
- 反模式：把"加了 X 涨了 Y%"直接写成功效；多个辅助手段叠加时不做交叉对照（互相替代的部分会被**重复计价**）。
- 溯源：vectordb-news 分块改造 A/B（2026-09-28，六配置全正向但辅助手段增益集体缩水）
