## 十五条元原则（跨场景，最高优先级）

1. **结构化优先**：凡是要 LLM 稳定遵循的属性（年龄/风格/格式），必须结构化存储（DB 列/枚举），注入 prompt 并进优先级表；自由文本字段不可靠。**反向同样成立**——要求模型**输出**的字段也必须显式声明结构（完整 schema + 枚举词表），否则模型只填提示词里点过名的那一个字段，下游分组/打分全部退化（2026-09-11 修订，见 L-10）。
2. **降级路径与主路径同等重要**：fallback 也要多样化、可识别、可救援；修 fallback 时必须检查主路径是否同样有病。
3. **状态三处一致**：内存变量、DB、前端展示。任何用户 override 都要问一句"写回 DB 了吗？"——后台异步任务只信 DB。
4. **异步任务的前端契约**：占位状态显式建模（如 `pending_enrich`），前端识别后走"生成中"分支 + 轮询（如 5s×6）；绝不把占位文本当最终结果，绝不显示"生成失败"，显示"生成中"。
5. **迁移幂等**：ALTER TABLE 前先查列是否存在；迁移脚本重跑不能炸。
6. **半截路检查**：新数据流必须贯穿 model → migration → API → caller 四层，只写 crud 层就是埋雷。
7. **复用不复制**：上游代码用动态引用（importlib + 独占 namespace + stub 注入），只引用纯函数；逐行复制 = 双份 bug 维护。
8. **部署三件事**：缓存策略（nginx Cache-Control + hash chunk）、MOCK 数据清理、可选依赖优雅降级（缺 SMTP/OAuth key 不崩，降级运行）。
9. **协作先行**：开源 PR 先沟通占坑 → 用数据回应 maintainer 顾虑 → 快速响应 review → 完整测试证据链。
10. **超时预算**：LLM read timeout 按 prompt 规模和 max_tokens 设定（复杂 prompt ≥60s）；警惕超时静默走 fallback——症状是"结果突然变短/变烂"，不是报错。
11. **工具读数二次确认**：诊断结论不能只依赖单一工具输出——控制台可能用错误编码渲染（GBK 渲染 UTF-8 制造"假性乱码"）、搜索可能跨同名副本串台（或对点目录/超大文件**静默 0 命中**，见 M-54）、命令行内联 JSON 可能被转义吞引号。改代码前必须用**第二种手段**交叉验证（换工具读同一数据源、打印 `repr()`/码点、比对文件行数与章节标题），否则会基于幻觉修坏本来正确的代码。
12. **对外宣称必须可验证、且三处同源**：README / 落地页 / 视频 / 宣传文案里的每一句"能力、路径、口径"，都要能指向**一条命令可复现**的验证手段（端点、文件行号、脚本）；只写"清单公开""支持 X"这类笼统话，就必须补上"在哪验、怎么验"。源码 / 文档 / 对外画面必须同源 —— 本次教训：视频卡片写 `/api/assistant/meta`，实际端点叫 `/api/assistant/status`，而这个错路径**同时躺在卡片源码里**，重渲一次就会再错一次。发现不一致时二选一：改口径，或补实现；**已发布物无法回改时，用可公开追溯的方式更正（评论区 / 更正说明），并把源头一起修掉**（2026-09-21 新增）。
13. **交付形态即验收对象**：验收必须打在"用户/评审真正会拿到的那一形态"上 —— 发布后**下载下来的资产**、冻结后的 exe、线上 URL；**本地构建通过 ≠ 发布物可用**（打包命令、产物结构、数据落盘位置都可能不同）。它是 E-08（本地 QA 根目录对齐生产前缀）、M-10（本地验证的假成功/假失败）的第三次同类出现，按"同一问题第三次出现即提升"入库：今后凡发布，必须补一次"下载资产 → 解压 → 运行 → 查版本/健康/页面"的闭环（2026-09-21 新增；**2026-09-26 补一条边界**：当本机网络**取不回**交付物时——例如 release 资产在受限网络下无法下载——退一步用“同一条构建命令产出的等价产物”做字节校验（本例：本地 `git archive` 的 zip 内脚本与本机实跑脚本 sha256 一致），并在交付说明里**显式声明未验证到的那一层**，别让“已验证”无限背书）。
14. **共享可写文件只追加、不重写**：同一个文件可能被多个会话/写者改时（当日日志、当日决策记录、共享配置），**永远不要整篇重写**——用文件末尾锚点做追加，且**写之前先读一次尾部**确认锚点还在、内容没被换掉。整篇重写会**静默吞掉别人的记录**，且事后只能靠"我记得写过"才发现；权威记录要落到仓库/带版本控制的地方（2026-09-26 新增，同族 M-28）。
15. **长任务先读系统守护的规则**：在装有"自动杀进程"组件（内存守护一类）的机器上跑长任务（构建/渲染/编译），开工前先读守护的**规则与阈值**，再选姿势：优先用其**可热加载的白名单**临时豁免（任务结束立刻恢复原状），其次限进程内存、让产物可续跑。进程一旦"静默消失"（无报错、无栈、日志停在半途），第一个取证对象是**守护自己的日志/告警文件**，而不是应用日志。它是 E-09（先查内存）→ E-18（按阈值设门禁）→ E-25（临时白名单豁免）第三次同类出现后的提升：前两次都在"被动适应守护"，白名单豁免才把它变成可协商的组件（2026-10-04 新增）。

   ```
   - 方案：<怎么修，保留关键代码/命令>
   - 反模式：<千万别这样做>
   - 溯源：<原始文档路径或会话日期>
   ```
2. 如果新经验验证/推翻了某条元原则，直接修改 SKILL.md 的原则条目并在末尾注明修订日期。
3. 同一问题第三次出现时，提升为元原则。
4. 收尾校验：同步 SKILL.md 中的条数声明，跑 `node scripts/check.js`——编号 / 索引 / 计数的 error 必须清零（历史条目缺字段的 warning 可暂留）。

**维护规则**：
- 每条经验必须带溯源，不可凭空写。
- 蒸馏时删业务细节，留通用规律；代码片段只留骨架。
- 元原则控制在 15 条以内，超了就合并。
